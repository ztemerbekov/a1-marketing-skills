# A1 Message Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a standalone public `a1-message` skill that drafts or rewrites one source-faithful workplace message an existing business contact can understand and answer without avoidable clarification.

**Architecture:** The installable package keeps entry and output contracts in `SKILL.md`, invariant stage order in one spine, and stage-specific source, structure, and QA rules in three focused references. Criteria-based evals protect the two input branches and the highest-risk boundaries; human documentation, neighboring-skill boundaries, and every applicable client catalog are updated together.

**Tech Stack:** Markdown Agent Skills, YAML OpenAI presentation metadata, JSON marketplace manifests, SVG A1 icons, Bash and Python repository validators.

**Spec:** `docs/superpowers/specs/2026-08-29-a1-message-design.md`

## Global Constraints

- Work only on branch `codex/a1-message`; do not create a GitHub Issue.
- The canonical directory and frontmatter name are exactly `skills/a1-message/` and `a1-message`.
- The final display name is exactly `A1 Message`.
- The skill is model-invoked: omit `disable-model-invocation` and omit `policy.allow_implicit_invocation`.
- Its one artifact is one compact workplace message for one existing business relationship and one communication job.
- It accepts either supplied source material or one selected workplace-message draft.
- It does not own cold first-contact outreach, public copy, a layered memo, specialist analysis, or multiple unrelated messages.
- Every fact, figure, decision, recommendation, owner, deadline, quotation, and causal claim remains traceable to an allowed source.
- Ask one concise question only when every accurate result would otherwise invent material content or choose between materially different meanings or decisions.
- Runtime files must not depend on repository design documents, maintainer evals, or another skill's private files.
- Do not attribute the skill to, cite, or name any external manifesto, restaurant group, or source personality anywhere in the branch's new product copy.
- Use the canonical support footer only after a successful final user-facing result, and suppress it for artifact-only output, boundary responses, clarification prompts, and unsuccessful runs.
- Before release to `main`, present every final manifest field and contact field for explicit maintainer approval; do not merge without that approval.

- [ ] **Step 5: Write the four runtime references with one canonical owner per concept**

`references/message-spine.md` must contain exactly these five ordered stages and their completion tests:

1. Confirm one recipient, one communication job, the supplied material, and explicit channel/format constraints. Complete when one recipient and one source-supported awareness, decision, action, or reply job determine what the message must enable.
2. Read `source-policy.md` and build the message map. Complete when every eligible substantive element has a source status and unsupported completion details are excluded.
3. Read `message-structure.md` and design the reading path. Complete when the opening stands alone and the rest answers the recipient's likely operational questions without repeating the source trail.
4. Draft or rewrite one compact message. Complete when what happened, why it matters, what is proposed or decided, what is required, and the supported next step are recoverable at a glance.
5. Read `final-qa.md` and revise. Complete when avoidable clarification caused by the message is removed and every substantive statement remains source-faithful.

`references/source-policy.md` owns:

- the current instruction, selected material, clearly applicable earlier conversation facts, and the first eligible Marketing Context source as the only allowed inputs;
- a message map separating main point, context, facts, problem, supplied options, recommendation, decision status, requested action, owner, deadline, risk, unknowns, and support;
- the distinction between supplied recommendation, decided action, awaiting approval, and unresolved choice;
- narrow derivation only when explicit source criteria make the conclusion non-arbitrary;
- one-question blocking only when accuracy otherwise requires invention or a material choice;
- safe progress with a material limitation outside the artifact when the gap affects use.

`references/message-structure.md` owns:

- priority order: main point, necessary context, proposed or decided response, timing, supporting detail;
- conclusion-first rewriting even when inputs are chronological;
- source processing: summarize a forward rather than reproducing it;
- optional blocks chosen by recipient questions rather than a mandatory template;
- compact messenger or ordinary business-email form;
- restrained bold emphasis only for a real decision, amount, deadline, or action anchor;
- operational next steps containing only source-supported actor, action, timing, dependency, and post-approval consequence;
- the target test that a fully assembled message should leave the recipient able to answer, decide, act, or acknowledge without preventable follow-up.

`references/final-qa.md` owns one exhaustive revision checklist grouped under Source Integrity, Communication Job, Reading Path, Prose and Scanability, and Output Integrity. It must verify traceability; distinguish proposals, recommendations, and decisions; preserve unknowns; put the main point first; retain necessary context; remove raw forwarding; make supported next steps operational; use bold only as structure; preserve requested tone and channel; and comply with `../SKILL.md`. End with an instruction to revise until every applicable item passes or ask the single blocking question when no accurate artifact is possible.
